# Operator panel

R21 displays candidate refusal codes and Russian explanations for both preparation Inspect and durable terminal results. Inventory facts (free, conservatively required and deficit units, configured bank policy) and action/time estimates come directly from planning. Three alternatives are shown first; the remainder are expandable. Inspect has a separate result timestamp and snapshot warning; saved results use observation freshness. Historical checkpoints without evidence show missing details. The bounded HTTP projection excludes raw planning assumptions and catalogs; it does not change selection, permissions or archival rules. Freeing space can expose another refusal and does not guarantee a feasible plan.

Set `Operator:Enabled=true` to expose `/operator` and `/operator/snapshot` on the existing host. The default is disabled. The panel accepts connections on the host’s configured listening addresses, including a server IP or LAN hostname; it does not enforce loopback-only clients or require login. The page uses embedded assets with no external dependencies, no-store responses and a restrictive content policy. It does not grant game-action permission or change the configured execution mode.

The panel reads `Execution:RunDirectory` for the configured API origin/character without acquiring the execution lease and without contacting the API. One shared reader refreshes at most once every two seconds; the page polls every two seconds and refreshes after commands; unchanged lists are retained instead of rebuilt. Atomic replacement can continue while a reader holds the old file. Each checkpoint read is capped at 8 MiB; up to 20 recent archived summaries are displayed. Missing or corrupt storage is distinct from an idle executor. Failed reads remove the previous successful projection; loss of the HTTP connection labels the previously displayed facts stale.

Worker activity comes from the local execution lifetime, not `/health/live`. A nonterminal checkpoint with no worker shows AwaitingRecovery. Confirmed actions come only from Verified journal entries; unresolved commands and incomplete timing remain explicit. Decisions, attempts, time including downtime, charged resources and milestone history come from durable facts. Old checkpoints lacking an observation timestamp show unknown freshness; new character reads/action responses persist optional ObservedAt. No migration or invented timestamps are applied.

The response projects known character fields, run ID, limits and lifecycle facts. Raw identity, catalogs, exception text and credentials are not exposed. The panel is for a trusted network. Network reachability is the access boundary; there is no login or per-user authorization. R16's historical intermittent failure remains open.

## Server access

Configure the existing ASP.NET host listener for the server's network interface (for example `--urls http://0.0.0.0:5080`) and open `http://<server-address>:5080/operator` from a client in the same trusted network. `Operator:Enabled=true` is still required; manual controls additionally require the settings below. Changing the UI access policy does not change the listener, firewall, game API permissions, execution mode or startup behavior. No internet-facing access or authentication is configured by this change. The separate legacy `/operation/stop` remains loopback-only; the panel uses `/operator/stop`.

## Explicit control (R18)

Additionally set `Operator:ControlsEnabled=true` with `Execution:Mode=Inspect`. This combination suppresses the startup worker: opening the host does not automatically inspect or act. Other combinations fail registration. Configure the noncombat Portfolio and API credentials on the server, and a dedicated absolute Execution:RunDirectory. The main form offers action/time limits and a single «Запустить» button. This explicitly requested action obtains a fresh Inspect receipt and immediately submits it to Start; users do not need to race the receipt expiry. «Посмотреть план» is an optional read-only preview in the expandable advanced section; its receipt is never reused for a later start. Preparation shows immediate progress, locks editable settings and prevents duplicate submissions. Refused Inspect never proceeds to Start; ambiguous network failures are shown without automatic command retries. Stop remains available while the executor is running. The page prepares a RunId (1–80 letters/digits/underscore/hyphen, first character alphanumeric) and positive finite bounds at or below Execution's configured ceilings, with MaxNoProgress <= MaxDecisions. Combat profiles are refused.

`GET /operator/controls` supplies a projected profile, permissions, stocks, ceilings and a per-process CSRF header token. `POST /operator/inspect` accepts RunId, MaxActions, MaxSeconds, MaxDecisions and MaxNoProgress. A Selected result returns an opaque receipt bound to the exact policy, origin/character, limits and permission configuration. `POST /operator/start` accepts `{ "Receipt": "..." }`. Receipts expire after FreshnessSeconds; configuration changes require another Inspect. The receipt does not bypass AllowActions or LiveActionsApproved. HTTP 409 carries a named refusal; HTTP 403 denies access.

All operator POSTs require `X-Artiact-Control` and same-origin browser metadata. The header token is supplied to the panel automatically; it is CSRF protection, not user authentication. No cross-origin policy is enabled. The separate legacy `/operation/stop` still requires local-address/Host and same-origin browser metadata; local non-browser CLI POSTs remain supported. A stop sent to that legacy route through a container bridge/remote interface is refused; invoke it from the host/container loopback boundary.

The coordinator owns one background execution; browser refresh/closure does not cancel it. A repeated receipt returns AlreadyAccepted, without another execution. Busy executors refuse other starts/Inspect. Start rechecks the local lease and durable identity; StagedExecution independently acquires the lease and preserves its own preflight, intent and retry rules. The same StagedExecution and archive guards serve CLI and panel.

“Продолжить сохранённый запуск” copies the durable RunId and all limits into the form for a new Inspect; it does not create a new run or refund budgets. Host restart discards receipts and preserves checkpoints. “Остановить” requests cancellation; a dispatched successful response is persisted before following work stops. “Сохранить итог в архив” passes the current identity digest to the shared lifecycle guard. Unknown, Cancelled and other Blocked runs remain protected; the specific Blocked/NoFeasibleCandidate outcome can be archived when the shared journal checks prove a finished outcome with no pending or unverified commands; the new-ID button does not clear an existing run. After successful archival, the form generates a new ID. Continuation, archival and ID management live in the advanced section with explanations; archival availability comes from the server’s CanArchive projection, using the same predicate as the archive write. Disabled archival displays an explanation. Finished runs cannot be resumed: the UI directs the operator to archive an eligible outcome, and Start returns RunFinished instead of accepting an execution that cannot act. The accepted-start message is replaced when a subsequent snapshot shows the final outcome. Archives preserve the original status/reason and bytes; archival does not claim goal completion. A new session can encounter the same lack of available goals. Host shutdown requests cancellation and awaits the owned task.

The existing [live protocol](autonomous-live-protocol.md) remains a separate gate. R19 preparation removed the arbitrary ten-decision minimum so the six-decision ceiling is accepted without increasing it. The real read-only autonomous preflight on 2026-09-08 returned AutonomousBudgetExhausted with zero attempts under the two-action scope; that initial scope did not execute actions. The subsequently approved R19 route passed through the [scoped live harness](scoped-operator-live.md); its exact evidence does not authorize another run.

Verification is recorded in the [R17 change](../openspec/changes/operator-observation/verification.md). Browser preview uses synthetic facts; it is not live acceptance. Do not start the main application as a compilation test.

R20 adds [finite series and local notifications](bounded-schedule.md). Its observation-only panel exposes series budgets, status, events and a guarded Stop button; manual run controls are mutually exclusive with scheduling. No live schedule is enabled by implementation or the earlier R19 approval.
