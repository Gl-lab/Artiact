# Цели от потребностей — R25

Режим включается явно через `Portfolio:Needs`; `Portfolio:AutonomousGoals` при этом оставляют `false`. Пустой список заказов не вызывает общую прокачку. Источники потребностей: абсолютный заказ оператора и наблюдаемый дефицит HP при отдельно разрешённом `Portfolio:Recovery`. Препятствие в рецепте создаёт дочернюю подготовку выбранного родителя, а не самостоятельную награду.

## Настройка и заказы

Пример фрагмента конфигурации (не включает разрешение игровых действий):

```json
{
  "Portfolio": {
    "AutonomousGoals": false,
    "Needs": {
      "Directory": "C:/ArtiactState/local-needs",
      "AllowCraft": true,
      "AllowBankWithdrawal": false,
      "Reserved": { "protected": 1 }
    }
  }
}
```

Для каждого API origin используйте отдельный абсолютный `Directory`. Внутри него `orders/<canonical-character-hash>.json` хранит версию 1 и до 128 заказов. Папку можно совместить с каталогом запусков: файлы заказов находятся в отдельном подкаталоге и не попадают в архив запусков. Чтение отсутствующего хранилища не создаёт файлов.

`Id` — стабильный идентификатор, `Code` — код предмета, `Quantity` — абсолютный требуемый запас сверх `Reserved`, `Priority` — 1–100, `Revision` — возрастающая версия. Статусы: `Active`, `Cancelled`, `Completed`. Если разрешено изъятие, доступный банковский запас учитывается один раз в удовлетворении заказа; это не обещание переместить готовый предмет из банка в сумку. Отменённые и выполненные ID не возрождаются. Новый заказ получает новый ID. Для одинакового кода цели абсолютные, не суммируются; запас защищается по максимальной активной цели.

При включённых ручных controls панель позволяет добавить и отменить заказ. `GET /operator/orders` возвращает книгу; `POST /operator/orders` принимает `{ "Order": { "Id": "one", "Code": "tool", "Quantity": 1, "Priority": 1, "Revision": 1, "Status": "Active" }, "ExpectedRevision": 0 }`. Действуют прежние same-origin и `X-Artiact-Control` guards. Запись сравнивает ревизию под отдельной файловой блокировкой, выполняет Flush и атомарную замену; конфликт возвращает 409. Завершение фиксирует только исполнитель по свежему наблюдению. Изменение заказа аннулирует неиспользованные Inspect receipts и не запускает игру.

## Поддерживаемая цепочка

Используются существующие производство, stock ledger, подготовка, банковские команды и Recovery. Полная цепочка оценивается на копии наблюдения до выдачи первой команды, включая последующие разрешения, вместимость, поездки, депозиты, изъятия и ингредиенты. Оценщик никогда не вызывает Dispatch. Постусловие каждой смоделированной команды должно пройти.

Подготовка поддерживает mining/fishing и weaponcrafting/cooking. Производство в новом оценщике ограничено weaponcrafting/cooking. Гарантированная добыча требует rate=1 и положительного min_quantity для каждого drop: запас увеличивается на минимум, вместимость проверяется по максимуму. Неизвестные эффекты, неподдерживаемые профессии, случайный выход, циклы и недоказанные пути отклоняются. Глубина плана заказа ограничена 16, шагов полного прогноза — 256; Recovery сохраняет собственные ограничения подготовки и до 32 вариантов пищи. Готовые запасы учитываются раньше новых действий, банк требует своего разрешения; Recovery может сравнить пищу с отдыхом. Для заказов сравниваются разрешённый банковский и локальный способы получения ингредиентов; каждый использует детерминированный рецепт и маршрут существующего production planner; перебор всех эквивалентных рецептов не добавлен.

Выбор: приоритет родителя (HP — 100), затем обратная полная оценочная стоимость времени, затем ordinal ID. Полезность родителя равна 1; ингредиенты и уровни не прибавляют награду. Материалы, защищённые запасы и вместимость — ограничения допустимости; стоимости разных материалов в денежном выражении нет. Общие ингредиенты резервируются один раз; будущие действия заново планируются из свежего фактического запаса.

XP оценивается по [официальным формулам навыков](https://docs.artifactsmmo.com/concepts/skills/); будущий порог XP повторяет наблюдаемый `max_xp`, поэтому дальнее обучение остаётся оценкой. Длительность: настроенные move/gather, craft 4 секунды за партию, bank 3 за код, use 3, rest по доле недостающего HP; применяется `UnknownMultiplier`. Возвращённые XP и cooldown остаются фактами, а не заменяются прогнозом. Несовпадение с прогнозом может остановить следующий срез.

## Срез, счётчики и завершение

Если поддерживаемый полный путь превышает бюджет, допускается конечный префикс с сохраняемым результатом: ингредиент, промежуточный предмет, минимальный подготовительный уровень или восстановление. Одно перемещение результата не даёт. Панель разделяет `FullActions/FullSeconds` и `SliceActions/SliceSeconds/SliceResult`, показывает причинную связь, последовательность оценённых шагов, приоритет, дефицит и требуемый/настроенный MaxNoProgress. Результат среза не объявляет весь заказ выполненным.

Проверка отсутствия прогресса повторяет порядок Tick: порог проверяется до действия; dispatch увеличивает счётчик, только подтверждённая Productive-команда сбрасывает. Подготовка сохраняет прежнюю семантику Productive. Учитываются уже потраченный NoProgress и решение для завершения. Недостаточный предел даёт `EstimatedNoProgressInsufficient` до действий. Смена родителя, среза и рестарт не возвращают бюджет. После среза нужен отдельный новый запуск, если текущий бюджет исчерпан; автоматической серии нет.

Inspect без потребностей возвращает `Stopped/NoActiveSupportedNeeds`, не создаёт checkpoint/receipt и не фиксирует terminal внутри сессии. Следующая проверка видит новый заказ. В Bounded такой исход сохраняется; повторное открытие не действует. Архив допускается только с проверенным журналом, согласованными счётчиками и отсутствием pending/unknown. Отдельная книга заказов переживает архивирование. Если заказ отменён во время отправленной команды, сначала сверяется прежний intent, затем прекращается подготовка. Повреждённые файлы не исправляются игровыми действиями.

R20 отклоняет этот профиль до запуска серии. Manual milestones и general development сохраняют прежние конфигурации и идентичность при отсутствии Needs. Версия `needs-v1` и её разрешения входят в identity; старые gathering checkpoint не становятся заказами. Live-исполнение новых цепочек и банка не выполнено; оно требует отдельной конкретной приёмки. Проверки и границы — [evidence R25](../openspec/changes/needs-driven-goals/implementation-evidence.md).
